# mm.cli: the `mm` command

Owns the terminal entry points, and the evaluation harness they run: matrices, batches of headless games and their reports. Run `uv run mm --help` for the commands and options.

**May import:** every layer.

**Entry points**
- `__init__.py`: the commands. `play` runs a game with scripted bots or Agents (with `--out`, its review is written beside it too) (`--provider claude`, or a whole `--lineup`), printing the transcript as it happens and saving events and model calls as NDJSON with `--out`, and `--replay` plays a saved game again from its recorded calls (see `docs/providers.md`); `serve` runs the API and prints the Host's link, which hands the browser the Host token (`MM_HOST_TOKEN`, or one kept in `runs/host-token`, made the first time); Ctrl+C, or SIGTERM on Linux, halts its games before their next decision, and they resume when it starts again; a second Ctrl+C stops at once, and games still resume, repeating only calls that were not recorded. `new-game` starts a game on a running API as the Host (`--host-token`, or the token `serve` uses), leaving the seed for the server to draw unless `--seed` is given; `export` writes a finished game's whole log from the server's database to a game file (NDJSON, the format `play --out` writes), which the console replays with no server, with its review beside it, and its model calls, so `play --replay` can play it again; `evaluate` plays a matrix of game configurations in batches into a run folder, resuming where the last batch stopped, and writes its report (see `docs/evaluation.md`); `schema` exports the protocol; `minds` writes the server's mind of each Resident after each reflection in the recorded fixture, which the console's tests check its own fold against.
- `recording.py`: the files beside a saved game (its model calls, its review) and how each is written (NDJSON as records happen, or JSON at once), the tally of model calls printed at the end, and `GameRecording`, which writes one game's files as it is played (for `play --out` and each game of an evaluation).
- `matrix.py`: an evaluation's `Matrix` (read from TOML): a base game configuration, the axes it varies (each combination a `Cell`, every cell on the same seeds) and the caps on a batch.
- `evaluation.py`: `play_batch`, which plays the games a run folder has not played yet, one at a time, until the batch's cap or the first aborted game, and the `RunFolder` (its matrix, its game files and the ledger of finished games, each tagged with the commit and prompts that played it).
- `report.py`: `write_report`, which reads every finished game's measures again from its files and writes the run's `report.md`: every rate pooled with its Wilson interval and sample sizes, the model calls' use as measurements, position bias, and the caveats; `charts.py` draws its SVG charts of town win rate.
- `transcript.py`: `describe(event)`, one readable line per event.

**Why it is shaped this way:** a headless game with a readable transcript is the fastest way to see a rule change working, without a browser.
